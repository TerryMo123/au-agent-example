## 第 2 页｜场景与真正难点

**标题**：经营问数，难在哪里？

### 知识点 · 典型问题形态

| 问题示例 | 能力诉求 |
|----------|----------|
| 近 7 天 Amazon US 的 GMV 是多少？ | 查数 + 指标口径对齐 |
| 哪些 SKU 低于安全库存？ | 诊断 / 规则，不只是列表查询 |
| 近 30 天 ACOS 超标的投放有哪些？ | 阈值扫描 + 结构化建议 |
| 退货政策里破损怎么处理？ | 内部制度检索 + 引用，禁止编造合规话术 |

### 知识点 · 核心难点（接模型容易，难在下列约束）

1. **答错成本高**  
   - 文案瑕疵可容忍；GMV / 补货建议错误会进入经营决策  
   - 优先「可核对的数据路径」，弱化纯自由生成  

2. **权限与脱敏**  
   - 同问异权：组长可看成本 / 海运 / 贡献利润；组员不可见  
   - 仅「登录即可问」会绕过数据权限体系  

3. **制度 + 数据常并存**  
   - 例：退货率上升 → 既要数，也要对政策/处理规范  
   - 对应能力：`hybrid`（SQL 与 RAG 非互斥）  

4. **延迟与费用**  
   - 全链路常见：路由 → 检索/SQL → embedding → 大模型生成  
   - 每问全跑 → TTFT 差、token 贵 → 需要路由分流 + 缓存  

5. **多轮追问**  
   - 典型短句：「换成近 30 天呢？」  
   - 单独做语义近邻易与其它时间窗问题「长得像」，但指代依赖上文  
   - 缓存设计的高风险点  

### 知识点 · 目标对比

| 维度 | 普通 Chat | 本项目目标 |
|------|-----------|------------|
| 生成方式 | 自由生成 | 路由可控 + Skill 结构化 |
| 可解释性 | 黑盒答案 | route / sources / 图表可复盘 |
| 失败表现 | 失败即空白或乱拼文案 | `degraded` 语义清晰 |
| 隔离 | 人人同答 | 角色 + 用户级隔离 |

## 第 3 页｜总体架构（前后端一张图）

**标题**：全链路鸟瞰

### 架构示意

```
前端 React（SSE 状态机 + 图表 + 会话）
        │  POST /chat/stream  (status / token / done / error)
        ▼
FastAPI ChatService
        │
        ├─ 语义缓存（exact → semantic；追问跳过 semantic）
        ├─ LangGraph：route → retrieve_sql / retrieve_rag → enrich → generate
        ├─ MySQL（业务数） / Chroma（制度知识）
        └─ Redis（缓存，可选）+ /ready + Prometheus
```

### 知识点 · 前端层

- 形态：经营问答**工作台**（非单气泡 Chat）  
- 状态机事件顺序：`status` → `token`* → `done`；异常：`error` + 降级标记  
- `status` 阶段例：routing / cache_lookup / retrieving_* / generating / cache_hit  
- `done` 载荷：answer、session_id、route、sources、metadata（图表、缓存、降级等）  
- 协议：SSE；接口：`POST /chat/stream`  
- 细节：原生 `EventSource` 难带 JWT → **fetch 读流**自解析（见第 7 页）

### 知识点 · 后端编排

- 编排中心：`ChatService`（模型不直暴露给前端）  
- 顺序：语义缓存查找 → 未命中再进 LangGraph  
- 图节点（路径可解释）：  
  | 节点 | 职责 |
  |------|------|
  | `route` | 判定 `sql` / `rag` / `hybrid` |
  | `retrieve_sql` / `retrieve_rag` | MySQL / Chroma；hybrid 下并行 |
  | `enrich`（hybrid） | 制度片段注入 NL2SQL / 生成，降低「有数但口径错」 |
  | `generate` | 流式成答 + 可视化 spec |

### 知识点 · 数据与运维面

- MySQL：经营指标与业务表  
- Chroma：政策 / 规范等向量知识  
- Redis（可选）：问答语义缓存  
- `/ready`：依赖深探针；Prometheus：阶段耗时 / TTFT / 缓存等  

### 后续深挖三刀（地图）

1. 路由：省成本 + 可解释  
2. 数据面：SQL 护栏 + Skill + 权限  
3. SSE + 缓存：体验与防串答

## 第 4 页｜深挖 1：智能路由 + Hybrid（约 8 分钟）

**标题**：先定路径，再花钱——规则优先的路由设计

### 知识点 · 设计前提

- 每问并非必须上最强模型、打开全部 Tool  
- 企业问数优先：**多数流量便宜、路径可解释、可复盘**  

### 知识点 · 三种路由

| route | 触发直觉 | 下游 |
|-------|----------|------|
| `sql` | 问数 / 指标 / 库存 / 广告花费等 | 库表 / Skill / NL2SQL |
| `rag` | 政策 / 合规 / 运营规范等 | 向量知识库 |
| `hybrid` | 双边信号都有，或单边不稳 | SQL∥RAG，再 enrich |

### 知识点 · 决策机制：规则优先，小模型兜底

- **规则层**（命中则不调路由模型）  
  - sql 信号例：GMV、ACOS、可售库存、近 7/30 天、退货率、库存预警…  
  - rag 信号例：退货政策、合规、管控规范…  
  - 收益：低延迟、省 token、结果可解释  
- **小模型兜底**：规则不确定时用路由模型（如 qwen-turbo）分类  
- **fallback**：保证链路不中断  
- **`route_via`**：`rule` | `llm` | `fallback`  
  - 前端展示例：「路由 sql·规则」  
  - 可解释性为一等公民（非仅日志字段）  

实现锚点：`app/agent/routing.py`

### 知识点 · Hybrid 专项

- 真实问题常为「数 + 制度」  
- 检索策略：SQL 与 RAG **并行**（相对串行降低 TTFT）  
- enrich：制度知识注入后续 NL2SQL / 成答  
- 目标：减少「数值对、口径/处置建议却是编的」  

### 知识点 · 取舍

| 选择 | 放弃 / 弱化 |
|------|-------------|
| 规则优先 + 小模型兜底 | 大模型完全自主选 Tool 的通用 Agent |
| 路径可观测、可演示 | 最大自主性优先 |

- **原则**：路由目标不是「最聪明」，而是 **大部分流量便宜且可解释；少数模糊题再付小模型税**

### Demo A · 验证点

| 步骤 | 输入 | 期望知识点验证 |
|------|------|----------------|
| 1 | `近 7 天 Amazon US 的 GMV 是多少？` | `sql` + `route_via=rule`；SQL/图表 Tag |
| 2 | `退货政策里破损如何处理？` | `rag`；知识库 / sources |
| 3 | `为什么某产品退货率上升？` | 常为 `hybrid`；SQL + 知识库同时出现 |

现场提示：指消息上绿色「路由」Tag 讲 `route_via`，优于贴大段代码。

## 第 5 页｜深挖 2：NL2SQL 安全与业务 Skill（约 8 分钟）

**标题**：问数可以，作恶不行——数据面护栏 + 专项 Skill

### 知识点 · 问题分层

- 路由解决「走哪条路」  
- 本页解决：  
  1. 执行层会不会打坏数据库  
  2. 高频诊断是否完全依赖模型临场发挥  

### 知识点 · NL2SQL 执行护栏

| 护栏 | 细节 |
|------|------|
| 只读意图 | 拒绝更新/删除类操作 |
| 危险关键字 | **词边界**匹配：降误杀列名片段，同时减少漏拦 |
| 表白名单 | 仅允许业务表白名单；角色叠加禁表 |
| 自动 LIMIT | 防止全表拖出打爆连接/内存 |
| 连接池 + 超时 | 含 `MAX_EXECUTION_TIME`；慢查询可终止 |

- **原则**：生成侧可宽松，**执行侧必须严格**

### 知识点 · 鉴权与数据权限

- 认证：JWT  
- 角色：`manager` / `user`  
- 组员约束例：  
  - 字段脱敏：成本、采购价、海运价、贡献利润等  
  - 资源/表禁止：部分运价、成本影响、采购明细等  
- 会话隔离：历史按 `user_id` 归属；越权 `session_id` → 统一 404（不存在）  
- 权限嵌在查询与会话层，而非仅前端菜单隐藏  

实现锚点：`app/auth/security.py`、`session_service`

### 知识点 · 业务 Skill（≠ 再包一层 prompt）

| Skill | 机制要点 | 前端可见 |
|-------|----------|----------|
| 库存预警 | 安全库存 / 库龄 / 在途等规则扫描 + 补货建议结构 | Tag：库存预警 |
| 广告诊断 | ACOS/ROAS 超标扫描 + 降出价/否定词建议 | Tag：广告诊断 |
| 退货归因 | 原因码分布 + 归因与处置建议 | Tag：退货归因 |

- 模型职责偏「组织表达」；**诊断逻辑由规则/阈值驱动**  
- 相对纯自由生成：更稳、更好回归  

### 知识点 · 指标口径

- 覆盖例：GMV、ACOS、可售库存等  
- 能力：别名对齐 + 算法提示注入 NL2SQL  
- 目标：降低「同词不同算法」  

### 设计原则（可投屏）

> 护栏在生成之前：先限制可触达数据，再限制可执行 SQL。

### Demo B · 验证点

| 步骤 | 操作 | 期望知识点验证 |
|------|------|----------------|
| 1 | 组员账号问成本/采购相关 | 脱敏或禁表生效 |
| 2 | `哪些 SKU 可售库存低于安全库存？` | Skill 结构 +「库存预警」Tag |
| 3 | `近 30 天广告 ACOS 超标的投放有哪些？` | 「广告诊断」Tag |
| 4 | （可选）组长同问对比 | 字段/资源可见性差异 |

现场提示：切号易冷场；时间紧只做步骤 2 或 3。

## 第 6 页｜深挖 3：SSE 全链路 + 缓存隔离（约 8 分钟）

**标题**：体验要快，答案不能串——流式协议与缓存设计

### 知识点 · 6A SSE 协议

**事件流**

```
status*  →  token*  →  done
              ↘ error + degraded（失败路径）
```

| 事件 | 内容要点 |
|------|----------|
| `status` | 阶段：routing / cache_lookup / retrieving_* / generating / cache_hit / degraded… |
| `token` | 增量正文 |
| `done` | answer、session_id、route、sources、metadata |
| `error` | 阶段失败信息；可带 `degraded` / `partial` |

**失败语义（关键）**

| 错误做法 | 正确做法 |
|----------|----------|
| 半截答案后硬拼 FALLBACK 文案 | 发 `error`，标记 `degraded`，保留已产出或明确降级文案 |
| 降级结果写入缓存 | **degraded 禁止入缓存**（防止故障被放大成「标准答」） |

**前端实现要点**

- 需求：POST + `Authorization`  
- 原生 `EventSource`：偏 GET、自定义头弱 → 不适用  
- 方案：`fetch` + ReadableStream，按行解析 `event:` / `data:`  
- 中断：AbortController  

实现锚点：`au-agent-web-example/src/api/client.ts`

### 知识点 · 6B 语义缓存

**目标与风险**

- 目标：重复问题加速、降低 LLM token  
- 风险：企业场景下「缓存用错」会造成高置信度错答  

**两级查找**

| 级别 | 机制 | 特点 |
|------|------|------|
| exact | 归一化（空白/标点/大小写）→ SHA256 | O(1)；**零 embedding、零大模型**；TTFT 最优 |
| semantic | 同作用域 embidx 余弦近邻 + 阈值 | 适合「换种说法问同一事」；有 embedding 成本 |

查找顺序：exact →（允许时）semantic → miss

**分片键演进**

| 阶段 | Key 维度 | 能防 | 防不住 |
|------|----------|------|--------|
| 早期 | `role` only | 组员命中组长敏感答 | 同角色跨用户互命中 |
| 当前 | `role + user_id` | 跨用户串答 | — |

- Redis key 形态例：`au:qa:exact:{role}:u{user_id}:{hash}`  
- 旧「仅 role」条目：payload 无 `user_id` → **一律不命中**（防串答）  

实现锚点：`app/services/semantic_cache.py`

**追问策略**

| 条件 | 行为 | 原因 |
|------|------|------|
| 会话已有历史（`is_follow_up`） | **跳过 semantic** | 短追问向量易撞车，指代靠上文 |
| 同上 | **整条不 store** | 防「换成近 30 天」污染该用户 embidx |

- 观测标签：`exact` / `semantic` / `semantic_skipped` / `miss`  

**原则（可投屏）**

> 缓存省 token；隔离保信任。追问依赖上文时，语义相似是高风险而非收益。

### Demo C · 验证点（需 `SEMANTIC_CACHE_ENABLED=true` + Redis）

| 步骤 | 操作 | 期望知识点验证 |
|------|------|----------------|
| 1 | 新会话问 GMV 原句 | 全链路生成；写入该用户缓存 |
| 2 | 再开新会话，同句/同义句 | `缓存命中·精确/语义`；明显加速 |
| 3 | 同会话追问：`换成近 30 天呢？` | **无** semantic 命中；`semantic_skipped` 路径 |
| 4 | （可选）换用户同句 | 不命中上一用户缓存 |

现场提示：步骤 3 是最佳懂的设计验证点；步骤 2 前确认 Redis 可用。

## 第 10 页｜Q&A 知识点速查

**Q：追问为何跳过 semantic？**  
- 追问短、向量易与其它时间/范围问句相近  
- 指代依赖上文 → 语义命中易成「高置信度错答」  
- 策略：有历史 → 跳过 semantic；追问结果不落库  
- exact 仅对完整原句复问仍可能生效；风险主要在近邻  

**Q：exact 为何先于 embedding？**  
- 归一化哈希，O(1)  
- 零 embedding、零大模型 → TTFT / 成本最优  
- 大量「原样再问」无需付向量税  
- semantic 作为 exact 未中的补充  

**Q：为何不端到端开放 SQL？**  
- 可生成，但执行前必须：只读、白名单、LIMIT、超时  
- 完全开放 ≈ 数据库暴露给概率模型  
- Skill：高频诊断 = 规则 + 查询 + 文案组织，利于稳定与回归  

**Q：hybrid 是否必然更慢？**  
- 检索并行，通常优于串行 sql→rag  
- 成本与延迟大头常在最终生成 token  
- 应用路由分流纯 sql/rag + 缓存挡重复问  
- hybrid 换正确性与覆盖，而非故意叠延迟  

**Q：与自主 Tool Agent 的差异？**  
- 本方案：LangGraph 显式状态 + 固定节点 → 可观测、可演示、可复盘  
- 问数场景优先「可控 + 可解释」  
- 自主 Agent 适合开放任务；选错 Tool / 乱写 SQL 代价更高  

**Q：距生产还缺什么？**  
- 时效分层 TTL（「今天 GMV」不可长缓存当真理）  
- SQL 结果二级缓存（进一步省库）  
- 更强多租户隔离  
- 评测集 + 回归（防改规则/prompt 后沉默变差）  
- 当前定位：关键设计验证闭环，非生产就绪宣称  

**Q：前端为何不用原生 EventSource？**  
- 需要 POST + JWT Header  
- EventSource 偏 GET、自定义头能力弱  
- 采用 fetch + ReadableStream 手写 SSE，并支持中断
