# 从「能聊天」到「能问数」
## 经营数据 Agent 的工程实践

- 场景：外贸家具经营问数 + 制度问答
- 形态：前后端联调的技术研究 Demo

## 只讲四个工程问题

- 编排如何可控、可解释

- 体验如何流式、可降级

# 经营问数，难在哪里？

- 答错成本高：数错进决策，不能纯靠幻觉
- 权限与脱敏：同问异权（组长 / 组员）
- 制度 + 数据常并存：需要 hybrid
- 全链路贵且慢：要路由分流 + 缓存
- 多轮追问短句：语义相似却依赖上文

---

# 目标对比：普通 Chat vs 问数 Agent

| 普通 Chat | 问数 Agent |
|-----------|------------|
| 自由生成 | 路由可控 + Skill 结构化 |
| 黑盒答案 | route / sources / 图表可复盘 |
| 失败即空白 | degraded 语义清晰 |
| 人人同答 | 角色 + 用户级隔离 |

# 深挖一：先定路径，再花钱

- 三种路由：sql / rag / hybrid
- 策略：规则优先，小模型兜底
- 规则能定案：不调用路由模型（省钱、可解释）
- 不确定时：小模型分类；再不行 fallback
- 前端可见：路由 + via（规则 / 小模型 / 降级）

---

# Hybrid：数与制度一起答

- 真实问题常是「查数 + 对规范」
- SQL 检索与 RAG 检索并行（降 TTFT）
- enrich：制度知识注入 NL2SQL / 成答
- 目标：减少「数对了，口径或建议是编的」
- 取舍：可控可复盘 > 最大自主选 Tool

---

# Demo：路由可解释

- 问 GMV → 期望：路由 sql · 规则 + 图表
- 问退货政策 → 期望：路由 rag + 引用 sources
- 问退货率为何上升 → 期望：常为 hybrid
- 验证点：消息上的路由 Tag，而非日志

# 深挖二：问数可以，作恶不行

- 生成可宽松，执行必须严格
- 护栏：只读 · 词边界危险词 · 表白名单 · 自动 LIMIT · 超时
- 权限：JWT + manager/user；字段脱敏；会话按 user_id 隔离
- Skill：库存预警 / 广告诊断 / 退货归因（规则驱动，非临场散文）
- 口径层：GMV、ACOS 等别名与算法对齐

# 深挖三：SSE 流式协议

- 事件序：status → token* → done
- 失败：error + degraded（半截答案不硬拼 FALLBACK）
- degraded 结果禁止写入缓存
- 前端：fetch 读流解析 SSE（POST + JWT；不用原生 EventSource）
- 可中断：AbortController

请配一张横向事件流示意图。

---

# 深挖三：缓存要快，更要防串

- 目标：重复问题加速、降 LLM token
- 两级：exact（哈希，零 embedding）→ semantic（近邻+阈值）
- 分片：role + user_id（同角色也不跨用户共享）
- 追问：有历史上文 → 跳过 semantic，且不落库
- 原则：追问依赖上文时，语义相似是风险不是收益

请配「exact → semantic」流程图，旁注追问跳过。

---

# Demo：缓存命中与追问

- 新会话首问 GMV → 全链路，写入用户缓存
- 另一新会话同句 → 缓存命中（精确/语义），明显更快
- 同会话追问「换成近 30 天」→ 不应语义命中
- 换用户同句 → 不命中上一用户缓存

（此页突出「追问不命中」为设计亮点）

# 前端：可解释的问答台

- 不是气泡墙：路由 / SQL / RAG / Skill / 缓存 / 降级 Tags
- 图表：后端 visualization spec → 前端 AntV 渲染
- RAG：sources 引用溯源
- 会话侧栏 + 鉴权；看板与 Agent 共用登录态
- 价值：复盘路径无需翻日志

# 刻意选择与刻意放弃

| 决策 | 选择 | 放弃 |
|------|------|------|
| 路由 | 规则优先 + 小模型兜底 | 纯自主选 Tool |
| 问数 | 护栏 + Skill | 完全开放 SQL |
| 体验 | SSE + 降级语义 | 只等最终 JSON |
| 缓存 | 用户分片 + 追问禁 semantic | 全局共享缓存 |
| 范围 | 垂直场景 Demo | 通用 Copilot |

- hybrid 是否更慢？→ 检索并行；贵在最终生成 token
